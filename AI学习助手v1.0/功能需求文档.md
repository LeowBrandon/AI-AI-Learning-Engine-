## 一、功能拆解与优先级

### 优先级定义

| 级别 | 含义 | 说明 |
|---|---|---|
| **P0** | 必须先做 | 缺了它整个产品跑不起来，或别的功能依赖它 |
| **P1** | 可以后做 | 不影响主链路闭环，等 P0 稳了再补 |
| **P2** | 最后做 | 依赖前面所有功能积累的数据 |

### 优先级总览

```
P0 ── 1. 传资料  ─┬─→  2. 聊资料
                  └─→  3. 做测评
                            │
P1 ── 4. 看进度  ←─────────┘（依赖测评产生的成绩数据）
        │
P2 ── 5. 出周报  ←（依赖进度与测评的历史数据）
```

**一句话逻辑**：没有资料就没有可聊、可考的内容；没有测评数据就谈不上进度；没有进度就写不出周报。

### 1. 传资料（P0）

| 编号 | 小功能点 | 优先级 | 说明 |
|---|---|---|---|
| 1.1 | 上传文件 | P0 | 可解析 **PDF、PPTX、Word(docx)、Markdown、TXT**；一次可拖入多份，前端逐个上传。旧版 .doc/.ppt 在上传时即被拒绝并提示另存为新格式 |
| 1.2 | 格式校验 | P0 | 非上述格式直接拒绝并提示；单文件上限默认 **200 MB**（`MAX_UPLOAD_MB`）。前端也会先拦一道，避免超大文件传到一半才被后端掐断 |
| 1.3 | 文本抽取 | P0 | PDF 取文字层、PPTX 取每页文字与表格、DOCX 取正文与表格、MD/TXT 直接读（自动识别 UTF-8 / GB18030） |
| 1.4 | 内容切片 | P0 | 按空行分段后攒成约 `CHUNK_SIZE`（默认 1200）字符一片；**不建检索索引**（见下方说明） |
| 1.5 | 拼接资料正文 | P0 | 回答与出题时，把所选资料的正文按 `MATERIAL_CONTEXT_LIMIT` 截断后直接拼进提示词 |
| 1.6 | 处理状态反馈 | P0 | 状态分「解析中 / 完成 / 失败」；有资料处于解析中时前端每 2 秒刷新列表，全部落定后停止 |
| 1.7 | 后台处理 | P0 | 上传后**立刻返回**（状态 `pending`），存文件→抽文字→切片→入库全在后台线程跑，用户不用等 |
| 1.8 | 资料列表 | P0 | 每行显示文件名、类型、大小、状态；供聊资料、测评选择范围 |
| 1.9 | 失败重试 | P0 | 解析失败的资料可重新提交解析 |
| 1.10 | 删除资料 | P0 | 数据库记录（含切片）与磁盘文件**一起删干净**；删除前二次确认 |
| 1.11 | 上传结果提示 | P0 | 每份文件上传后弹出提示，说明成功或失败原因 |

> **为什么 1.3 / 1.4 是 P0**：文件本身不是「资料」，能被送进提示词的文本才是。没有抽取，聊资料只能靠模型瞎编。

> **关于检索：本版明确不使用向量模型、不做 RAG。**
> 「聊资料」的实现方式是——把所选资料（或全部资料）的正文按字符上限截断后，
> 整段拼进系统提示词交给大模型。所以：
> - `material_chunks` 不存 embedding，切片只用于分块存储与按上限截断；
> - 回答里的「依据」列出本次实际拼进提示词的资料，不再标注具体段落号；
> - 资料总量超过 `MATERIAL_CONTEXT_LIMIT` 时会被截断，需在界面上提示用户。

### 4. 看进度（P1）

| 编号 | 小功能点 | 优先级 | 说明 |
|---|---|---|---|
| 4.1 | 总体概览 | P0 | 一排 5 张统计卡：资料总数、已掌握份数、学习次数、平均分、薄弱点个数 |
| 4.2 | 知识点雷达图 | P0 | 各知识点的掌握度画成雷达图（知识点少于 3 个时不出图，给提示） |
| 4.3 | 知识点明细列表 | P0 | 每个知识点显示名称、进度条、百分比、掌握等级 |
| 4.4 | 薄弱知识点 | P0 | 得分率低于 0.7 的知识点单独成区，按得分率升序 |
| 4.5 | 资料详情与笔记 | P0 | 每份资料一个笔记框，**停笔约 1.2 秒自动保存，无需点保存按钮** |
| 4.6 | 笔记缩略 | P0 | 笔记超过 4 行时出现滑块，拖动控制可视行数（缩略 ↔ 完整） |
| 4.7 | 按资料看进度 | P1 | 每份资料是「未开始 / 学习中 / 已测评」及对应得分（**本版前端未使用**） |

### 掌握等级口径（4.3 / 4.4 用）

按知识点累计得分率 `score_rate` 划分：

| 等级 | 条件 | 颜色 |
|---|---|---|
| 已掌握 | `score_rate ≥ 0.9` | 绿 |
| 熟练 | `0.7 ≤ score_rate < 0.9` | 金 |
| 待加强 | `0.4 ≤ score_rate < 0.7` | 橙 |
| 薄弱 | `score_rate < 0.4` | 红 |

- **薄弱知识点** = `score_rate < 0.7`（即「待加强」与「薄弱」两档），按得分率升序排列。
- **已掌握资料数** = 该资料关联的知识点全部达到「熟练」及以上（`score_rate ≥ 0.7`）的资料数；
  尚无作答记录的资料不计入。
- **学习次数** = 对话次数 + 测评次数。

## 二、后台接口清单

统一约定：

- 前缀 `/api`，请求与响应均为 JSON（上传除外，用 `multipart/form-data`）。
- 时间字段统一 ISO 8601 字符串。
- 失败响应统一为 `{ "error": { "code": "XXX", "message": "人话描述" } }`。
- 下表「优先级」与第一节的功能优先级对应。

### A. 资料相关

#### A1. 上传资料 —— P0

```
POST /api/materials
Content-Type: multipart/form-data
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| file | File | 是 | 表单字段名固定为 `file`；一次传一份，多份由前端逐个调用 |

**可解析的格式**：`pdf` / `pptx` / `docx` / `md` / `markdown` / `txt`

**旧版格式在上传这一步就拒绝**（不是收下再异步失败）：

| 扩展名 | 返回 code | 提示 |
|---|---|---|
| `.doc` | `LEGACY_FORMAT` | 旧版 .doc 无法解析，请用 Word 另存为 .docx 后重新上传 |
| `.ppt` | `LEGACY_FORMAT` | 旧版 .ppt 无法解析，请用 PowerPoint 另存为 .pptx 后重新上传 |
| 其它 | `BAD_FILE_TYPE` | 不支持的文件格式：.xxx |

> Python 生态里没有可靠的 .doc/.ppt 二进制解析器。前端仍允许选中这两种文件，
> 以便拿到这句可操作的提示，而不是笼统的「格式不支持」。

**返回**（HTTP 201）

```json
{
  "id": 12,
  "name": "Transformer架构详解.pdf",
  "file_type": "pdf",
  "file_size": 2458123,
  "status": "pending",
  "error_msg": null,
  "chunk_count": 0,
  "note": "",
  "created_at": "2026-09-18T21:20:00+08:00"
}
```

> **上传即返回**，返回时状态必然是 `pending` —— 这正好证明没等解析完。
> 存文件、抽文字、切片、入库全在后台线程里跑，前端轮询 A2 获取最新状态。
>
> 状态流转：`pending`（已收到，排队中）→ `processing`（正在解析）→ `ready` / `failed`。
> 前端把 `pending` 与 `processing` 都显示为「解析中」。

#### A2. 资料列表 —— P0

```
GET /api/materials
```

**返回**

```json
{
  "items": [
    {
      "id": 12,
      "name": "Transformer架构详解.pdf",
      "file_type": "pdf",
      "file_size": 2458123,
      "status": "ready",
      "chunk_count": 86,
      "note": "我自己的学习笔记，可为空",
      "created_at": "2026-09-18T21:20:00+08:00"
    }
  ]
}
```

> `note` 一并返回，供「进度」页的笔记区直接渲染，省去逐份请求。

#### A3. 资料处理状态 —— P0

```
GET /api/materials/{id}/status
```

**返回**

```json
{ "id": 12, "status": "ready", "chunk_count": 86, "error_msg": null }
```

`status` 取值：`pending` 排队中 / `processing` 处理中 / `ready` 可用 / `failed` 失败。

#### A4. 资料详情 —— P1

```
GET /api/materials/{id}
```

**返回**：同 A2 单项，另附 `chunks_preview`（前若干片段，便于确认抽取是否正常）。

#### A5. 失败重试 —— P0

```
POST /api/materials/{id}/retry
```

**参数**：无（资料 ID 在路径里）

**返回**

```json
{ "id": 12, "status": "pending" }
```

> 把 `status = failed` 的资料重新排入解析队列并**立刻返回**，状态回到 `pending`。
> 对 `ready` 的资料调用返回 400 `ALREADY_READY`。

#### A6. 删除资料 —— P0

```
DELETE /api/materials/{id}
```

**返回**

```json
{ "deleted": true, "id": 12 }
```

> 删除资料及其全部切片。前端在调用前需二次确认。

#### A7. 保存资料笔记 —— P0

```
PUT /api/materials/{id}/note
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| note | String | 是 | 笔记全文；传空字符串表示清空笔记 |

**返回**

```json
{ "id": 12, "updated_at": "2026-09-18T22:10:00+08:00" }
```

> 前端在用户停笔约 1.2 秒后自动调用，无需用户点保存。
> 离开「进度」页时会立刻补发一次，避免丢笔记。

### B. 聊资料相关

> **发消息（B1）是最核心的接口**，流程固定为五步：
> **搜资料 → 拼上下文 → 调 AI → 存消息 → 返回结果**。
> 每一步的实现位置：`context.select_relevant()` → `prompts.learner_system()` →
> `llm.chat()` → `_save_messages()` → `jsonify(...)`。

#### B0. 创建对话 —— P0

```
POST /api/chat/sessions
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| material_ids | Array\<Integer\> | 否 | 本次会话限定的资料范围；不传 = 全部资料 |
| title | String | 否 | 会话标题，不传默认「新对话」 |

**返回**（HTTP 201）

```json
{
  "id": 7,
  "title": "新对话",
  "material_ids": [12],
  "created_at": "2026-09-19T16:31:40+08:00"
}
```

> 前端目前用的是**懒创建**：点「新对话」只清空界面，第一次发消息时由 B1 顺手建会话。
> 这样历史列表里不会堆一串空的「新对话」。这个接口留给需要显式建会话的场景。

#### B1. 提问 —— P0

```
POST /api/chat
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| session_id | Integer | 否 | 不传则新建会话 |
| material_ids | Array\<Integer\> | 否 | 限定资料范围；不传或空数组 = 全部资料 |
| question | String | 是 | 用户问题 |

**返回**

```json
{
  "session_id": 7,
  "answer": "自注意力机制的核心是……",
  "references": [
    {
      "material_id": 12,
      "material_name": "Transformer架构详解.pdf",
      "chunk_index": 12,
      "snippet": "……"
    }
  ],
  "no_reference": false,
  "created_at": "2026-09-18T21:25:00+08:00"
}
```

> `no_reference = true` 表示资料中未检索到相关内容，此时 `answer` 为「资料里没有提到」类回复。

#### B2. 会话列表 —— P1

```
GET /api/chat/sessions
```

**返回**

```json
{
  "items": [
    { "id": 7, "title": "自注意力的作用是什么", "material_ids": [12], "created_at": "..." }
  ]
}
```

#### B3. 会话消息 —— P1

```
GET /api/chat/sessions/{id}
```

**返回**

```json
{
  "session_id": 7,
  "messages": [
    { "role": "user", "content": "自注意力的作用是什么？", "created_at": "..." },
    { "role": "assistant", "content": "...", "references": [], "created_at": "..." }
  ]
}
```

#### B4. 删除对话 —— P0

```
DELETE /api/chat/sessions/{id}
```

**返回**

```json
{ "deleted": true, "id": 7, "message_count": 6 }
```

> 会话连同里面的消息一起删掉（`chat_messages.session_id` 上配了 `ON DELETE CASCADE`）。
> 前端历史对话列表目前**还没有删除入口**，需要补一个删除按钮才能用上这个接口。

### C. 测评相关

#### C1. 生成试卷 —— P0

```
POST /api/quizzes
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| material_ids | Array\<Integer\> | 是 | 从哪几份资料出题；传全部可用资料的 ID 表示「全部资料」 |
| question_count | Integer | 是 | 题目总数，取值 5 / 8 / 10 / 15；题型分配由后端决定 |

**返回**

```json
{
  "quiz_id": 31,
  "question_count": 10,
  "total_score": 10,
  "questions": [
    {
      "id": 301,
      "seq": 1,
      "type": "choice",
      "difficulty": "medium",
      "question": "……",
      "options": { "A": "……", "B": "……", "C": "……", "D": "……" },
      "full_score": 1
    },
    {
      "id": 305,
      "seq": 5,
      "type": "judge",
      "difficulty": "easy",
      "question": "……",
      "options": { "A": "正确", "B": "错误" },
      "full_score": 1
    },
    {
      "id": 309,
      "seq": 9,
      "type": "short",
      "difficulty": "hard",
      "question": "……",
      "full_score": 1
    }
  ]
}
```

**字段说明**

| 字段 | 取值 | 说明 |
|---|---|---|
| type | `choice` / `judge` / `short` | 见下方「选项格式」 |
| difficulty | `easy` / `medium` / `hard` | 前端显示为「简单 / 中等 / 较难」标签 |

### 选项格式（统一约定）

**`options` 一律是对象，不是数组**：`{"A": "选项文本", "B": "选项文本", ...}`。
选项文本**不带「A.」前缀**，字母由前端单独渲染成圆形标记。

| 题型 | options | 作答值 |
|---|---|---|
| `choice` | 4 个，A~D | 选项字母，如 `"B"` |
| `judge` | **固定 `{"A": "正确", "B": "错误"}`**，不由模型生成 | **布尔** `true` / `false`（前端把 A 映射成 true） |
| `short` | 无此字段 | 文本 |

> 模型出题时给的仍是数组 `["A. 文本", ...]`（提示词里就是这么要求的），
> 后端 `normalize_choice_options()` 会归一化成对象再落库。
> 它同时能吃下数组、对象、JSON 字符串三种输入 —— 模型偶尔不听话。
>
> 前端 `normalizeOptions()` 也做了一层同样的归一化，
> 所以即便后端将来又换了形状，界面也不会崩。

> **注意**：此接口返回的题目**不含 `answer` 与 `explanation`**，防止前端泄露答案。

## 四、AI 大脑：四套系统提示词

四套提示词分别对应四个调用场景，互相独立、不共用。
`{{...}}` 是运行时由后台注入的变量。代码在 `backend/prompts.py`。

### 实现约定

**1. 提示词里的「# 输入」块要拆开用。**
文档里的提示词把输入也写在一起，但多轮对话必须分开：角色与规则放 system，
资料放 system 末尾，学员的问题作为 user 消息。否则每轮都要重建 system，历史对话没处放。

**2. 模板占位符用 `{{name}}` + `str.replace` 填充，不能用 `str.format`。**
提示词里有 JSON 示例，含大量裸的 `{` `}`，`format` 会直接抛异常。

**3. 选择题与判断题的分数在本地精确判定，不交给模型。**
模型偶尔会把错的判成对，这种错误用户一眼就能看见。做法是：
题目与作答照常发给模型（拿它的 `reason` / `hit_points`），
但 choice/judge 的 `is_correct` 与 `score` 由后端按标准答案算；
简答题才用模型给的分数，并归到 0 / 0.5 / 1 三档。

**4. 调用失败自动重试。**
只对网络问题、HTTP 5xx、429 重试；4xx 是请求本身有问题，重试没意义。
重试次数由 `LLM_MAX_RETRIES`（默认 3，即总尝试 4 次）与 `LLM_RETRY_DELAY`（默认 1.5 秒，
实际等待 = 基数 × 第几次）控制。

**5. 模型返回的 JSON 要清洗。**
它经常在 JSON 外面包一层 ` ```json ` 围栏，或者前后加一句解释。
后端先剥围栏，再截取第一个 `{`/`[` 到最后一个 `}`/`]`，然后才解析。
解析失败也计入重试预算 —— 再问一次通常就好了。

**6. 段落的检索方式。**
不用向量、不做 RAG：按关键词重合度（英文按单词，中文按 2~4 字滑窗，词长即权重）
给每个切片打分，按分数从高到低填充，凑到 `MATERIAL_CONTEXT_LIMIT` 为止。
一个词都没命中时（如「总结一下」）退化成按顺序取前面的段落。
出题场景没有「问题」可依据，改用等间隔抽样，保证覆盖整份资料而不是只取开头。

### 提示词二 · 出题官（做测评）

```text
# 角色
你是「AI 学习助手」的出题官，为一名正在学习大模型课程的学员出题。

# 唯一出题依据
- 所有题目必须严格基于给定的资料片段，不得引入资料之外的知识。
- 每道题必须标注：来源资料编号 material_id、资料出处（资料名 + 片段定位）、考查的知识点。
- material_id 必须与资料内容里标出的【资料 N】编号完全一致，不得自己编。
- 资料不足以支撑某类题目时，少出或不出，并在返回中说明原因。

# 题型与要求

## 1. 单选题（choice）
- 4 个选项，有且只有一个正确答案。
- 干扰项必须来自资料中的相近概念，不得凭空捏造。
- 考查理解，不出纯粹照抄原文的题。

## 2. 判断题（judge）
- 一句陈述，答案只能是 true 或 false。
- 错误项要设计成「常见误解」，而不是明显离谱的表述。

## 3. 简答题（short）
- 要求学员用自己的话说明一个概念、机制或流程。
- 满分 1 分，必须写出可判断的评分要点。
- 不出没有标准答案的开放讨论题。

# 难度
每道题必须标注 difficulty，取值只能是 easy / medium / hard：
- easy：资料中直接陈述的事实或定义。
- medium：需要理解机制、区分相近概念。
- hard：需要综合多处内容或辨析常见误解。

三种难度都要出现，数量按下方给定值分配，不要清一色 medium。

# 题型分配
各题型的数量由后端算好后明确给出（配比 1/2 选择 + 1/4 判断 + 1/4 简答），
你只需严格按给定数量出题，不要自行调整。

> 为什么不让模型自己分：它算不准，分配错了前端看到的题型比例就不对。
> 后端 `distribute_counts()` 按 `choice = round(n/2)`、`judge = round(n/4)`、
> `short = n - choice - judge` 算出，再写进提示词。

# 输出格式
只输出 JSON，不要任何解释文字，不要 Markdown 代码块标记。

{
  "questions": [
    {
      "type": "choice",
      "difficulty": "medium",
      "material_id": 12,
      "question": "题干",
      "options": ["A. …", "B. …", "C. …", "D. …"],
      "answer": "B",
      "explanation": "为什么选 B，其他选项错在哪",
      "knowledge_point": "知识点名称",
      "source": "资料名 · 片段定位"
    },
    {
      "type": "judge",
      "difficulty": "easy",
      "material_id": 12,
      "question": "一句陈述",
      "answer": true,
      "explanation": "判断依据",
      "knowledge_point": "知识点名称",
      "source": "资料名 · 片段定位"
    },
    {
      "type": "short",
      "difficulty": "hard",
      "material_id": 13,
      "question": "提问",
      "answer": "参考答案",
      "scoring": ["要点一（0.5 分）", "要点二（0.5 分）"],
      "knowledge_point": "知识点名称",
      "source": "资料名 · 片段定位"
    }
  ]
}

# 禁止
- 禁止出现资料中没有的概念、数字、论文名、工具名。
- 禁止出答案有歧义或一题多解的题。
- 禁止把同一考点重复出成多道题。

# 输入
资料片段：
{{retrieved_chunks}}

出题要求：
- 单选题：{{count_choice}} 道
- 判断题：{{count_judge}} 道
- 简答题：{{count_short}} 道
- 简单约 {{count_easy}} 道、中等约 {{count_medium}} 道、较难约 {{count_hard}} 道
- 合计 {{question_count}} 道，每题 full_score 均为 1

# 任务
严格依据上述资料片段，按给定数量分配题型与难度出题。
```

### 提示词三 · 阅卷官（改卷）

```text
# 角色
你是「AI 学习助手」的阅卷官。你的任务是对照标准答案，批改学员作答。

# 总原则
- 只按给定的标准答案与评分标准判分，不引入资料外的判断。
- 判分从严从准，不因鼓励而送分。
- 每道题都必须给出判定理由。

# 分题型判分规则

## 1. 单选题（choice）
- 与标准答案完全一致 → 满分。
- 不一致 → 0 分。不做「意思接近」的宽容判定。
- 未作答 → 0 分。

## 2. 判断题（judge）
- 与标准答案一致 → 满分。
- 不一致 → 0 分。
- 未作答 → 0 分。

## 3. 简答题（short）
- 满分 1 分，只允许三个档位，不得给出 0.25、0.75 等中间值：
  · 1 分：答出全部评分要点，表述准确。
  · 0.5 分：答出部分要点，或要点齐全但表述有明显偏差、关键术语错误。
  · 0 分：答错、答非所问，或未作答。
- 判定只看「评分要点是否命中」，不看字数多少，不看表达是否优美。
- 学员用自己的话表述但意思命中要点 → 算命中，不要求与原文一致。

# 输出格式
只输出 JSON，不要任何解释文字，不要 Markdown 代码块标记。

{
  "results": [
    {
      "question_id": 1,
      "type": "choice",
      "user_answer": "B",
      "correct_answer": "B",
      "score": 1,
      "full_score": 1,
      "is_correct": true,
      "reason": "简短判定理由",
      "knowledge_point": "知识点名称"
    },
    {
      "question_id": 4,
      "type": "short",
      "user_answer": "学员原文",
      "correct_answer": "参考答案",
      "score": 0.5,
      "full_score": 1,
      "is_correct": false,
      "hit_points": ["要点一"],
      "miss_points": ["要点二"],
      "reason": "命中要点一，遗漏要点二",
      "knowledge_point": "知识点名称"
    }
  ],
  "summary": {
    "total_score": 8.5,
    "full_score": 10,
    "weak_points": ["知识点A", "知识点B"]
  }
}

# weak_points 判定规则
- 某知识点下所有题目得分率不满 100% → 计入 weak_points。
- 按得分率从低到高排序，最多保留 5 个。

# 禁止
- 禁止修改题目或标准答案。
- 禁止给出评分标准之外的分数。
- 禁止在 JSON 之外输出任何内容。

# 输入
题目与标准答案：
{{questions_with_answers}}

学员作答：
{{user_answers}}

# 任务
按上述规则逐题判分，并汇总未掌握知识点。
```
